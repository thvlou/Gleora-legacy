## 3. 트러블슈팅

> AI와 협업하며 실제로 막혔던 지점과 해결 과정.
> **원인 오진 → 재조사 → 정정**한 사례도 그대로 남긴다. 그 과정 자체가 기록의 가치.

### T1. Figma 손그림 테두리가 코드 변환에서 뭉개짐

**증상** 흔들리는 손그림 테두리가 매끈한 사각형으로 변환됨

**원인** 그 테두리는 CSS `border`가 아니라 **수천 개의 작은 채움 폴리곤**. Figma MCP의 Tailwind 번역이 이를 `border`로 단순화

**해결** `download_assets`로 SVG 원본을 받아 `?raw`로 인라인. 이후 모든 손그림 요소에 동일 방식 적용

**교훈** 디자인 툴의 코드 변환은 "비슷하게 보이는 것"으로 대체할 수 있다. 벡터 원본을 봐야 한다

---

### T2. CSS Modules가 전역 키프레임 참조를 조용히 삼킴

**증상** 로딩 화면의 눈 아이콘 회전 애니메이션이 아예 재생 안 됨. **에러도 안 남**

**원인** `.module.css` 안의 `animation` 속성에 적힌 이름은, **그 파일에 `@keyframes` 정의가 없어도 토큰 자체가 해시로 치환**된다. 전역에 정의해둔 키프레임을 참조하면 매칭되는 규칙이 없어 무시됨

**해결** 키프레임을 **참조하는 모듈 파일 안에 같이 정의**. 인라인 style로 참조하는 것만 전역에 유지

**교훈** 조용히 실패하는 버그가 제일 찾기 어렵다. `getComputedStyle().animationName`을 찍어보고 실제 `@keyframes` 규칙과 대조해서 발견

---

### T3. 관련 state를 쪼갰더니 배치 업데이트에서 새어나감

**증상** Submit 버튼 회피 동작이 첫 클릭 이후 먹통

**원인** `dodgeSide`와 `dodging`을 **두 개의 `useState`로 분리**해둔 것

**해결** 하나의 객체 state로 합치고 항상 새 참조를 반환하도록 변경

**검증 방법** React Fiber의 `memoizedProps.onClick` 참조 동일성을 클릭마다 비교하고, 별도 리스너로 native click이 실제로 매번 발생하는지 확인 → 환경 문제가 아닌 **진짜 코드 버그**임을 먼저 확정

### T4. 호버로 도망가는 버튼은 클릭이 불가능하다

**증상** URL이 아닐 때 Submit 버튼이 도망가는 기능 — 호버만 해도 사라져서 클릭 자체가 안 됨

**해결** 트리거를 `onHoverStart` → `onClick`으로 변경. 도망가면서 동시에 submit도 호출해 에러 문구가 뜨게 함

**교훈** "장난스러운 인터랙션"이 기본 기능을 막으면 안 된다

### T5. 클램프 경계가 붕괴해 커서 추적이 한 점에 고정

**증상** 이름이 긴 항목(`SPACE TYPE GENERATOR`)에서 3D 로고가 커서를 놓치고 한 자리에 멈춤

**원인** 카드 폭(629px) > 컨테이너 폭(606px)이 되면 `halfW > rectWidth - halfW`가 되어,
`Math.min(Math.max(x, halfW), Math.max(rectWidth - halfW, halfW))`의 상·하한이 같은 값으로 무너짐

**해결** 두 경계를 각각 `Math.min`/`Math.max`로 명시해 범위를 항상 유효하게 유지

### T6. "투명 벽에 튕기는" 현상 — 오진했다가 전수조사로 진짜 원인 발견

**증상** 커서를 우측으로 옮기면 로고가 보이지 않는 벽에 튕기듯 순간이동

**1차 오진** T5의 연장선(긴 이름만의 문제)으로 판단

**재조사** 26개 항목 전부에 대해 커서 위치를 0~1280px까지 쓸어가며 위치 변화량을 계산
→ **전 항목에서 예외 없이 396px 순간이동** 발생. 짧은 이름도 마찬가지였음

**진짜 원인** "오른쪽 공간이 부족하면 카드를 커서 왼쪽으로 뒤집는" 로직.
뒤집히는 지점에서 위치가 정확히 `2 × offsetX`(400px)만큼 점프

**해결** 부호 반전 로직 제거, 항상 `+offsetX`를 쓰고 클램프에만 위치 제한을 맡김
→ 전 항목 최대 변화량이 샘플 간격 수준(완전히 매끄러움)으로 감소

**교훈** **증상이 특정 케이스에서만 눈에 띈다고 원인도 거기 있는 건 아니다.** 전수 조사가 결과적으로 더 빨랐다

### T7. overflow 클립은 content box가 아니라 padding box 기준

**증상** `REFERO`의 마지막 `O` 끝이 잘려 보임

**원인** `<a>`가 텍스트 advance폭에 fit-content로 잡히는데, 폰트의 **실제 잉크 폭이 그보다 최대 2px 초과**(O·S·G 같은 둥근 글자). `overflow: hidden`이 그걸 잘라냄

**1차 시도 실패** `overflow-x: visible` / `overflow-y: hidden`으로 축 분리 시도
→ **CSS 스펙상 한쪽이 `visible`이면 다른 쪽이 강제로 `auto`로 계산됨.** `auto`도 경계에서 잘리므로 효과 없음 (라이브로 찍어보니 실제 `auto`였음)

**해결** overflow 클립 영역이 **padding box**라는 점을 이용해 `padding-right: 4px` 추가

**측정** 캔버스 `measureText`로 26개 전부의 advance폭 대비 잉크폭 초과량을 실측
(최대 1.92px — TEXT CRYSTLIZER, SPACE TYPE GENERATOR)

### T8. CSS 이징은 키프레임 구간마다 새로 적용된다

**증상** 흘러내리는 피가 3단계로 뚝뚝 끊김

**원인** 키프레임을 `0/35/70/92/100%` 다섯 구간으로 나눠뒀더니 **ease-in이 네 번 리셋**

**해결** `from`/`to` 단일 구간으로 두고 이징을 한 번만 태움

**교훈** CSS 애니메이션의 timing-function은 전체가 아니라 **키프레임 쌍 사이마다** 적용된다

### T9. 브라우저 자동완성이 입력값을 바꿔치기

**증상** Slack에 사용자가 입력한 URL이 아니라 `http://localhost:3000`이 도착

### T10. 자동화 브라우저의 `document.hidden` — 검증 방법론 자체를 바꿔야 했던 문제

**증상** 자동화 브라우저에서 애니메이션·위치 변화가 전혀 관측되지 않음. 코드가 틀린 것처럼 보임

**원인** 검증용 브라우저 창은 `document.hidden === true`라 **`requestAnimationFrame`과 CSS 트랜지션이 억제**된다. framer-motion 스프링, 직접 만든 관성 루프, `Wanderer`의 위치 갱신이 전부 rAF 의존이라 한 프레임도 진행 안 함

**해결 — 검증 우회 기법**
| 상황 | 방법 |
|---|---|
| 상태 전이 확인 | **React Fiber의 `memoizedState`/`memoizedProps` 직접 읽기** |
| 애니메이션 존재 확인 | `getAnimations()` + `getComputedTiming()` |
| 드래그 계산 검증 | 스프링 출력이 아니라 **원본 목표값(`rawOffset`)을 직접 읽기** |
| 이벤트 핸들러 검증 | 합성 이벤트 디스패치 대신 **`__reactProps$`의 핸들러를 직접 호출** |

**실제 사례** 모바일 드래그 검증 시 스프링 결과(`offset`)는 0에 멈춰 있었지만, 원본값(`rawOffset`)은 손가락 이동에 정확히 1:1로 반응(0→20→40→...→120)하는 것을 확인해 **로직이 옳음을 증명**

**교훈** 도구가 관측을 못 하는 것과 코드가 틀린 것은 다르다. **관측 계층을 바꿔서 증명**할 수 있다

### T13. Vercel 업로드 rate limit

**증상** 배포 시 `Too many requests - try again in 24 hours (api-upload-free)`

**원인** git 저장소가 아니라서 `.gitignore`가 적용되지 않아 **`node_modules`(285MB)를 파일 단위로 업로드**하려 함
→ 무료 플랜의 업로드 요청 한도(5000회/24h) 소진

**해결**
1. `.vercelignore` 생성 (`node_modules`, `dist` 등 제외)
2. `--archive=tgz` 옵션으로 **통짜 압축 1회 업로드**로 전환

### T15. 병렬 스캔의 rate limit 오탐 — 교차 검증으로 확인

### T16. DNS만으로는 못 잡는 "팔린 도메인"

**증상** 메타데이터 수집 중 `blackformat.com`의 제목이 `BlackFormat.com is for sale | HugeDomains`

**교훈** 링크 헬스체크는 **HTTP 상태 코드만으로 불충분**하다.
콘텐츠 수준의 검증이 필요하며, 이는 향후 헬스체크 기능(F5) 설계에 반영해야 한다

**발견 경위** 메타데이터 수집(533개) 결과의 제목을 훑던 중, 디자인 사이트여야 할 곳에서
태국어·그리스어 도박 사이트 제목이 나옴

**탐지 결과**

| 유형 | 도메인 | 현재 상태 |
|---|---|---|
| 🚨 스팸 탈취 | `28blacks.com` | 태국어 도박(UFABET) 사이트 |

**시사점**
1. 앞서 보안 검토에서 경고한 "만료 도메인 재등록 공격"이 **이미 실제로 일어나 있었다**

3. → `PRD-v1.md` F5(헬스체크)에 **콘텐츠 수준 검증** 요구사항 반영 완료

```
사망 판정:  DNS NXDOMAIN  또는  404/410  또는  콘텐츠 패턴 매칭
                                            (도박·성인·매물·파킹 키워드)
생존 판정:  403/429/401  ← 봇 차단일 뿐이므로 사망으로 처리하면 대량 오탐
```

### T19. 헤더와 카드가 서로 다른 레이아웃 계에 있었다

**증상** "상단 로고와 마진값 위계를 맞춰달라"는 요청에 실측해보니 기준선이 셋으로 갈려 있었다.

| 요소 | 왼/오른쪽 여백 |
|---|---|
| 로고 | 100px |
| Hit me | 104px |
| 카드군 | 116px |

**원인 1 — Hit me 4px** `.hitBtn`의 `padding: 10px 4px` 때문에 라벨이 버튼 안쪽으로 4px 밀려 있었다.
`.hitWrap`은 기준선에 정확히 붙어 있었지만, 눈에 보이는 건 버튼 박스가 아니라 라벨이다.
→ `right: calc(var(--side-margin) - 4px)` 로 padding만큼 상쇄.

**원인 2 — 카드군 116px (진짜 문제)** 코버플로는 고정 px 트랜스폼 + 중앙정렬이라,
카드군의 좌우 여백이 뷰포트 폭의 절반에서 상수를 뺀 값이 된다.

    카드 여백 = 뷰포트폭 / 2 − 596      (596 = scale 1 일 때 중심~바깥 카드 끝, 실측)

즉 여백이 **뷰포트 폭에 그대로 끌려간다.** 실측·계산 결과:

| 뷰포트 | 카드 여백 |
|---|---|
| 1200px | 4px |
| 1424px | 116px |
| 1920px | 364px |

`--side-margin`을 116px로 바꿔 맞추려던 첫 판단은 틀렸다. **한 해상도에서만 성립**하기 때문이다.

**해결** 마진을 카드에 맞추는 대신, 카드군을 스케일해서 마진에 맞췄다.

    scale = clamp(0.70, (뷰포트폭 / 2 − side-margin) / 596, 1.35)

약 1030~1810px 구간에서 카드 여백이 `--side-margin`과 정확히 일치한다.
그 바깥은 상·하한에 걸려 여백이 벌어지지만, 카드가 화면 대비 과하게 커지거나 작아지는 것을 막는다.
상·하한은 "카드가 뷰포트 폭에서 차지하는 비율"이 1424px 기준(약 0.35)에서 크게 벗어나지 않는 선으로 잡았다.

**검증** 1424px에서 로고 100 / Hit me 100 / 카드 좌 100 / 카드 우 100.
휠 한 노치에 한 칸 이동(WEB → UI)도 정상, 이동 후에도 여백 100 유지.

**교훈**
- 정렬 요청이 오면 **어긋난 값 하나를 옮기기 전에 전부 실측**한다. 여기선 세 값이 갈려 있었고, 그중 하나는 뷰포트 의존이었다.
- `position: fixed` + 고정 마진(헤더)과 중앙정렬 고정 크기(카드)는 **서로 다른 레이아웃 계**다.
  한 해상도에서 숫자를 맞추면 정렬된 것처럼 보이지만, 창 크기만 바꿔도 무너진다.
- 측정 자체도 함정이 있었다. `navigate` 직후 같은 batch 안에서 잰 값(712/199)은
  진입 애니메이션이 안 끝난 상태였다. 별도 호출로 다시 재야 정확한 값(100/100)이 나온다.
  → 트랜지션 있는 UI는 **측정과 렌더 트리거를 같은 호출에 두지 않는다.**

### T20. 배경이 카드 그림자를 죽이고 있었다

**증상** 배경색 추천 요청. 고르기 전에 기존 값을 재보니 문제가 있었다.

    페이지 배경  #0a0a0a  → 명도 10 / 255
    카드 배경    #1a1a1a  → 명도 26 / 255
    카드 그림자  rgba(0, 0, 0, 0.55) 0 26px 60px

**원인** 그림자는 검정이라 배경보다 어두워지는 방향으로만 작동한다.
배경이 이미 10/255면 **0까지 10단계밖에 못 내려간다.**
카드를 띄우려고 넣은 60px 블러 드롭섀도가 사실상 보이지 않는 상태였다.
카드와 배경의 명도차도 16단계뿐이라, 카드 윤곽은 `0 0 0 1px rgba(255,255,255,0.06)`
링 하나가 거의 전부 감당하고 있었다.

**후보 비교** 배경을 들어올려 그림자에 여유를 주는 방향으로 5개를 만들어 실제로 띄워 봤다.

| | 값 | 명도 | 성격 |
|---|---|---|---|
| A | `#0a0a0a` | 10 | 원래 값. 평평, 그림자 안 보임 |
| B | `#121214` | 18 | 단색. 여유 최대 |
| **C** | `#0e1014` | **16** | **채택.** 단색 + 쿨 틴트 |
| E | radial `#191a20` 중앙 | ~26 | 스테이지 비네트, 은은 |
| F | radial `#212128` 중앙 | ~40 | 스테이지 비네트, 강하게 |

**결정** C. 그림자 여유는 10 → 16 으로 늘고, R14 G16 B20 의 청색 기울기(+6)가 더해진다.
팔레트 9색이 주황·빨강·노랑 쪽으로 따뜻해서, 중립 회색보다 대비가 붙으면서
경쟁하는 색상을 새로 끌어들이지 않는다.

여유만 보면 B(18)가 C(16)보다 낫다. C 는 그 2단계를 틴트와 맞바꾼 선택이다.
비네트(E·F)는 가장자리가 어두워지는 방향이 카드가 z 로 물러나는 방향과 같아
깊이를 밀어주지만, 단색의 평평함을 유지하는 쪽을 택했다.

**구현** 후보를 `:root` 에 `--bg-a` … `--bg-f` 로 모아두고 `--bg` 한 줄로 스왑되게 했다.
지운 뒤 다시 만드는 것보다 남겨두는 편이 싸다.

**검증** 로고 100 / Hit me 100 / 카드 좌 100 / 카드 우 100 (T19 정렬 유지), 카드 5장.

**교훈**
- **어두운 배경에서 드롭섀도는 "배경 명도 − 0" 만큼만 쓸 수 있다.** 순검정에 가까울수록
  그림자는 무의미해진다. 다크 UI 에서 그림자로 부양감을 주려면 바닥을 먼저 들어올려야 한다.
- 색 추천을 요청받았을 때 **취향을 고르기 전에 현재 값이 제 역할을 하는지부터 잰다.**
  여기선 "무슨 색이 예쁜가"가 아니라 "왜 그림자가 안 보이나"가 진짜 질문이었다.
- 밝은 배경은 검토 대상이 아니었다. `.cfDim` 이 순검정 오버레이고 라벨 스크림도
  `rgba(0,0,0,0.7)` 이라, 이 구조는 다크를 전제로 짜여 있다.

### T21. 유광 배경 — 광원 방향은 이미 카드가 정해놓고 있었다

**요청** 배경을 유광 효과가 있는 블랙으로.

**먼저 확인한 것 두 가지**

1. **그레인이 어디 있나.** `.cfGrain` 은 카드 내부 요소였다(페이지 아님).
   매트 텍스처가 페이지에 깔려 있었다면 유광과 정면으로 충돌한다. 페이지는 비어 있어 진행 가능.
2. **광원 방향이 이미 있나.** 있었다. `.cfSheen` 이 전 카드 공통으로

       radial-gradient(130% 80% at 18% 6%,  rgba(255,255,255,0.26), transparent 58%)
       radial-gradient( 90% 60% at 88% 96%, rgba(0,0,0,0.20),       transparent 62%)

   **좌상단 하이라이트 / 우하단 그림자.** 배경 스페큘러를 다른 방향으로 넣으면
   카드와 배경이 서로 다른 조명 아래 있는 것처럼 읽힌다. 방향을 여기 맞췄다.

**후보** 전부 2레이어(스페큘러 + 베이스), 베이스는 T20 에서 고른 쿨 틴트 유지.

| | 스페큘러 | 베이스 | 성격 |
|---|---|---|---|
| **G1** | `radial 90% 70% at 20% 4%` α0.10 | `#0c0e12` | **채택.** 넓고 부드러운 좌상단 광 → 우하단 감쇠 |
| G2 | `radial 60% 45% at 24% -4%` α0.17 | `#08090c` | 좁고 밝은 블룸. 웻룩. 대비 강함 |
| G3 | `linear 168deg` α0.075 | `#0a0b0e` | 위에서 훑는 레이킹 광. 방향성 약함 |

**결정** G1. 스페큘러 중심 `20% 4%` 가 카드 `.cfSheen` 의 `18% 6%` 와 거의 일치해서
배경과 카드가 한 광원 아래 있는 것으로 읽힌다.
G2 는 단독으로는 더 예쁘지만 블룸 중심이 더 높고 좁아 카드와 안 맞는다.
G3 는 좌우 방향성이 없어 카드의 좌측광과 미묘하게 어긋난다.

**레이어 수 — 확인하지 못한 부분** 3레이어(스페큘러 + 우하단 감쇠 + 베이스 그라디언트)를
시도하자 스크린샷 캡처가 30s 타임아웃으로 재현성 있게 실패했다. 2레이어는 통과.
다만 **이게 실제 성능 문제인지는 검증하지 못했다.** 탭이 `document.hidden === true` 라
rAF 가 억제된 상태이고(이 프로젝트에서 반복된 조건), 브라우저 페인은 화면에 표시돼야
컴포지팅을 해서 그쪽으로도 측정이 막혔다. 즉 **숨은 탭의 온디맨드 래스터 한계일 가능성이 있다.**
보이는 탭에서는 문제없을 수도 있다. 확인 전까지는 안전하게 2레이어로 간다.

**구현** `--bg-g1` ~ `--bg-g3` 를 `:root` 에 추가, `--bg` 한 줄로 스왑.
`--bg-a` ~ `--bg-f`(T20 후보)도 그대로 둔다.

**검증** 로고 100 / Hit me 100 / 카드 좌 100 / 카드 우 100, 카드 5장, 베이스 `rgb(12,14,18)`.

**교훈**
- **배경 광택을 넣기 전에 이미 씬에 광원이 있는지 본다.** 여기선 카드가 좌상단광으로
  이미 정해놓고 있었고, 배경은 거기 따라가는 쪽이지 새로 정하는 쪽이 아니었다.
- 캡처 실패를 성능 문제로 단정하지 않는다. `document.hidden` 인 탭은 래스터 조건이
  달라서, 보이는 탭의 성능을 대신 말해주지 않는다. **모르는 건 모른다고 적는다.**

### T22. 로고 유리 반사 — 글자가 안 나뉜 SVG 에 글자별 효과 넣기

**요청** 로고가 글자 하나하나 유리판에 올라온 서체인데,
기존 폰트·컬러·크기·설정값을 벗어나지 않고 좌 → 우로 유리에 빛 반사되듯 반짝이게.

**막힌 지점** 로고는 `<img src="/gleora-logo.svg">` 이고, SVG 안은

    <g id="Logo"><path id="Gleora" d="..." fill-opacity="0.65" /></g>

**path 가 하나뿐이다.** 글자가 분리돼 있지 않아 인라인화해도 글자별 타겟팅이 안 된다.

**해결 — 원본을 건드리지 않는 마스크 오버레이**
`<img>` 는 그대로 두고, 같은 자리·같은 크기의 형제 `div.logoGlint` 를 얹어
**로고 SVG 자체를 `mask-image` 로 써서** 로고 실루엣 밖을 잘라낸다.
그 안에서 좁은 사선 광띠가 좌 → 우로 지나간다.

    폰트·색·크기·오퍼시티 = 원본 그대로. 빛만 위에 더해진다.

부수 효과 하나가 유용했다. 마스크로 쓰는 SVG 의 path 에 `fill-opacity="0.65"` 가 있어
**광택 농도가 로고와 같은 65% 를 자동으로 따라간다.** 따로 맞출 필요가 없었다.

합성은 `mix-blend-mode: screen`. 어두운 배경에서 screen 은 사실상 가산이라
원본 색을 어둡게 하거나 색상을 틀지 않는다 — "색에서 벗어나지 않게" 조건을 만족한다.

**튜닝 — 폭과 위치가 얽혀 있었다**
처음엔 띠 엘리먼트 자체를 좁혀서(`width: 38%`) 밴드를 만들었다.
폭을 20%, 14% 로 바꿔 비교하려 하자 **밴드가 화면에서 사라졌다.**
`translateX(%)` 는 자기 폭 기준이라, 폭을 바꾸면 같은 키프레임에서도 위치가 같이 밀린 것.

→ 띠를 `width: 100%` 로 고정하고 **밝은 구간만 그라디언트 스톱으로 좁혔다.**
이제 `-100%` = 완전히 왼쪽 밖, `+100%` = 완전히 오른쪽 밖으로 폭과 무관하게 예측 가능하다.

**밝기·폭 비교** (같은 위치에서 고정 후 비교)

| 폭 / α | 결과 |
|---|---|
| 24% / 0.50 | 넓고 흐릿. 단어 전체가 들뜸 |
| **18% / 0.80** | **채택.** 순간마다 글자 1~2개만 스침. 나머지 색 그대로 |
| 12% / 0.95 | 날카롭지만 번쩍임에 가까움 |

5s 주기 중 앞 1.4s 만 훑고 나머지는 쉰다 — 계속 움직이면 산만하다.
`background-position` 이 아니라 `transform` 으로 움직인다(리페인트 대신 컴포지팅).
`prefers-reduced-motion: reduce` 에서는 숨긴다.

**검증과 그 한계**
광택 박스가 로고와 완전히 일치(100, 44, 130, 30.61), 마스크·블렌드·애니메이션 등록 확인.
`animation-delay` 를 음수로 넣고 정지시켜 0.40 / 0.62 / 0.82 / 1.05s 를 캡처,
밴드가 좌 → 우로 이동하는 것을 확인했다.
다만 **실제로 매끄럽게 도는지는 못 봤다.** 탭이 `document.hidden` 이라
`animation.currentTime` 이 0 에서 안 올라간다. 키프레임과 기하는 맞지만
보이는 탭에서의 체감은 직접 봐야 한다.

**측정 도구 자체의 함정 (T19 에서 이어짐)**
검증 중 `getBoundingClientRect` 가 카드 여백을 719 / 200 으로 돌려줬다.
같은 시점 스크린샷에서는 좌우 모두 약 100px 로 정상이었다.
hidden 탭에서는 3D 변환된 요소의 레이아웃 박스가 갱신되지 않은 채 읽힌다.
**이 조건에서는 스크린샷이 ground truth 다.** 수치만 믿고 "깨졌다"고 판단하면 오진한다.

**교훈**
- SVG 가 단일 path 라도 **마스크로 쓰면 그 실루엣이 그대로 효과의 경계가 된다.**
  원본에 손대지 않고 효과를 얹는 가장 안전한 경로다.
- 원본의 `fill-opacity` 는 마스크 알파로 그대로 넘어온다. 제약이 아니라 공짜 정합성이다.
- `translateX(%)` 는 **자기 폭 기준**이다. 크기와 위치를 같이 조절하려 하면 서로 얽힌다.
  움직이는 요소는 폭을 고정하고, 모양은 내부에서 바꾼다.

### T23. Feature Card 내부 효과(.feature-fx) 통합

**요청** 전달 문서에 따라 9개 카드 내부에 시각 효과·인터랙션만 삽입.
카드 크기·배치·carousel·라벨·클릭 로직은 수정 금지.

**삽입 위치** 카드는 JS 로 생성된다. 기존 레이어 순서를 유지한 채 한 칸만 끼웠다.

    card.append(fill, fxEl, sheen, grain, grad) → titleBox → dimEl
                      ^^^^ 여기만 추가

`.cfFill`(그라디언트) 위, `.cfSheen`/`.cfGrain`/`.cfGrad`/라벨/`.cfDim` 아래.
카드의 광택·그레인·가독성 스크림·비활성 딤이 fx 위에 그대로 얹혀 재질감이 유지된다.

**Active 연결** 새 state 를 만들지 않았다. `render()` 안에 이미 있던 `isActive` 분기를
그대로 재사용해 `.feature-fx` 의 class/aria/inert 만 토글한다. 카드 transform 은 무관.

**막힌 지점 3개**

1. **키 불일치.** 문서는 "Font" 인데 프로젝트 키는 `type`(라벨 TYPE).
   라벨은 수정 금지이므로 `FX_KEY = { type: "font" }` 매핑만 두고 라벨은 그대로 뒀다.

2. **PHOTO 자산 없음.** 프로젝트에 사진이 하나도 없다.
   흑백 → 컬러 reveal 을 보여주려면 이미지가 있어야 하므로 SVG mesh 그라디언트를
   data URI 로 만들어 자리표시자로 넣었다. `FX_PHOTO_SRC` 한 줄 교체 지점.
   base/reveal 이 같은 이미지를 공유하므로 자산은 하나면 된다.

3. **라벨 충돌.** 문서의 하단 요소가 기존 카드 라벨 자리와 겹쳤다.
   `offsetLeft/Top` 으로 실측(3D 변환·컴포지팅 영향 없는 레이아웃 좌표):

   | 카드 | 요소 | 박스 | 라벨 |
   |---|---|---|---|
   | UI | `.fx-ui-stepper-object` | 40,294 112x70 | 22,343 27x34 |
   | GRAPHIC | `.fx-graphic-meta` | 45,346 92x22 | 22,338 83x42 |
   | TYPE | `.fx-font-specimen` | 40,356 420x8 | 22,341 49x37 |

   라벨은 못 건드리므로 **fx 내부 요소만** 비켜 놓았다 —
   스테퍼·메타는 위로(`bottom: 19%` / `20%`), 스펙시먼은 라벨 오른쪽에서 시작(`left: 32%`)
   시켜 라벨과 같은 baseline 을 공유하게 했다. 각 Feature 의 사양은 그대로다.

**검증**

| 항목 | 결과 |
|---|---|
| fx 개수 / is-active / inert | 9 / 1 / 8 |
| 비활성 카드에서 도는 애니메이션 | 0 |
| 신규 keyframe 접두 | 전부 `ffx-` (기존 `logoGlint`, `rv-drip` 와 무충돌) |
| 라벨 충돌 | 0 (수정 후 재실측) |
| UI 오브젝트 상호 충돌 | 0 |
| 측면 카드 클릭 → 이동 | WEB → UI 정상 |
| 활성 카드 컨트롤 조작 | 스위치/탭/칩/슬라이더/스테퍼 전부 동작, carousel 안 움직임 |
| 휠 한 노치 | ui → graphic (1칸) |
| 카드 수 / 좌우 여백 | 5 / 100·100 (T19 정렬 유지) |
| 콘솔 에러 | 없음 |

**inert 가 클릭 통과를 만든다** 비활성 카드의 fx 는 `inert` 라 hit test 에서 제외된다.
그래서 측면 카드의 fx 영역을 클릭하면 그 아래 `.cfFill` 이 맞고, 카드로 버블링해
기존 `handleCardClick` 이 그대로 돈다. 별도 처리 없이 이동이 유지되는 이유다.

**교훈**
- 전달 문서의 좌표는 **그 문서가 가정한 빈 카드 기준**이다. 기존 카드에 이미 라벨이
  있으면 하단 영역은 이미 점유돼 있다. **삽입 전에 점유 영역을 실측**해야 한다.
- 문서와 프로젝트의 용어가 어긋날 수 있다(Font vs TYPE). 라벨을 문서에 맞추는 게 아니라
  **매핑 한 줄로 흡수**하는 쪽이 규칙 위반을 피한다.
- 이번에도 `getBoundingClientRect` 는 전환 중 stale 값(카드 좌 214 등)을 돌려줬다.
  레이아웃 기준인 `offsetLeft/offsetTop` 은 정확했다. **hidden 탭에서 기하를 잴 땐
  offset* 를 쓴다.** (T22 에서 이어짐)

### T24. COLOR 카드 — CSS 박스로는 못 만드는 형태가 있다

**요청** 3D 렌더 데이지 레퍼런스처럼. 꽃잎 6장, 화이트 배리에이션 + 한 장만 `#B9F97A`,
메인 꽃은 좌측으로 돌아간 각도, 두 송이가 카드 중앙에 떠 있는 느낌.
꽃잎 분리 + HEX 노출 인터랙션은 유지.

**처음에 잘못 판단한 것** "COLOR 피쳐인데 꽃잎을 흰색으로 하면 주제가 사라진다"고 보고
**형태만 레퍼런스, 색은 팔레트 8색**으로 진행했다. 사용자가 원한 건 흰색이 맞았다.
문서 스펙(8색 꽃잎)을 근거로 삼았지만, 스펙보다 그 자리에서의 지시가 우선이다.

**CSS 박스의 한계** `border-radius` + 그라디언트로 4~5회 반복하며 계속 어긋났다.

| 시도 | 결과 |
|---|---|
| 넓은 흰 하이라이트 | 꽃잎이 우유빛으로 떠서 겹친 부분이 비치는 것처럼 보임 |
| 하이라이트 축소 + 채도 강화 | 젤리빈 |
| 매트 음영 + 중앙 능선 | 사탕 |

측정해보면 `opacity: 1`, `mix-blend-mode: normal` 로 **완전 불투명**이었다.
비쳐 보인 건 파스텔 톤과 이웃 꽃잎의 드롭섀도가 만든 착시.
결국 문제는 투명도가 아니라 **곡면을 만들 수 없다는 것**이었다.
사각 박스를 아무리 둥글려도 스푼처럼 휜 꽃잎 실루엣과 그 위의 방향성 음영은 안 나온다.

**해결 — 버튼은 유지, 안쪽만 SVG**
`.fx-petal` 버튼 구조·`--r` 회전·호버 13px·HEX 는 그대로 두고,
버튼 안에 `<svg viewBox="0 0 48 96">` 를 넣어 path 로 꽃잎을 그렸다.

    M24 96 C18 84 4 66 4 44 C4 18 14 2 24 2 C34 2 44 18 44 44 C44 66 30 84 24 96 Z

버튼 배경·radius·box-shadow 를 모두 제거해 히트 영역이 사각형이 아니라
**path 자체**가 되었다. 기존 인터랙션 코드는 한 줄도 안 바뀌었다.

**광원 일치** 꽃잎이 `--r` 만큼 돌아가 있으므로 그라디언트를 그대로 두면
꽃잎마다 빛 방향이 따라 돈다. `gradientTransform="rotate(-r 0.5 0.5)"` 로 되돌려
여섯 장 전부 한 광원에서 빛을 받게 했다.

**3D 각도** SVG 는 3D 가 없다. 대신 꽃 래퍼에 CSS `perspective()` + `rotateY/X/Z` 를 걸었다.
꽃잎이 전부 같은 평면이라 원근 투영이 정확히 먹고, 가까운 꽃잎이 더 크게 나온다.
앞 꽃 `rotateY(-26deg)`, 뒤 꽃 `rotateY(24deg)` — 서로 반대쪽을 본다.

**부수 버그** 뒤 꽃을 `opacity: .72` 로 어둡게 했더니 **뒤에 깔린 줄기가 꽃잎을 뚫고 비쳤다.**
어둡기를 색 자체에 넣고 불투명하게 되돌렸다.

**줄기 접점** `rotateX` 때문에 꽃술의 투영 중심이 계산값과 어긋난다(162 → 169 로 7px).
계산이 아니라 실측 좌표에 SVG 패스를 물렸다.

**중앙 정렬** 꽃 두 송이 + 줄기의 bbox 중심을 실측해 카드 중심에 맞췄다.
최종 bbox x 140~359 / y 41~360 → 중심 (250, 200) = 카드 중심.

**최종 색** 화이트 5종 + 액센트 1종.
`#FFFFFF` `#FAF6EC` `#F2EEE3` `#FDFAF2` `#EDE9DC` + `#B9F97A`

**교훈**
- **도구를 바꿔야 할 때를 알아야 한다.** 같은 방향으로 4~5회 조정했는데도 계속
  어긋나면 파라미터 문제가 아니라 매체의 한계다. CSS 박스 → SVG path 로 바꾼 뒤
  한 번에 해결됐다. 더 일찍 갈아탔어야 했다.
- **껍데기만 바꾸면 인터랙션은 공짜로 보존된다.** 버튼·변수·호버 규칙을 그대로 두고
  내부 렌더링만 교체하니 검증할 것이 형태뿐이었다.
- 문서 스펙과 그 자리의 지시가 부딪히면 **지시가 우선**이다. 스펙을 근거로 사용자의
  의도를 추측해 바꾸지 않는다.

### T25. 개화 애니메이션 — fill-mode 를 절반만 써야 했다

**요청** 액센트 잎을 `#7EE01D` 로. 그리고 하단에서 줄기부터 자라 꽃이 피어오르는 애니메이션.

**구성** 총 1.4s, `.is-active` 에서만.

| 구간 | 대상 | 시점 |
|---|---|---|
| 줄기 자람 | 4개 path | 0 → 760/900ms |
| 봉오리 맺힘 | 꽃술 2개 | 640 / 820ms |
| 꽃잎 펼침 | 12장, 스태거 | 720 + i×60ms / 900 + i×80ms |

**줄기** `pathLength="1"` 로 정규화하고 `stroke-dashoffset` 을 **-1 → 0**.
음수 오프셋이라 path 의 끝(화면 아래)부터 그려진다. 길이를 잴 필요가 없다.

**꽃잎** `transform-origin` 이 이미 밑동(50% 100%)이라 `scale(.12) → scale(1)` 만으로
중심에서 바깥으로 펴지는 움직임이 나온다. 별도 좌표 계산이 없다.

**fill-mode — 여기서 한 번 틀렸다**

처음엔 fill-mode 를 아예 안 썼다. 끝값이 기본 CSS 와 같으니 `forwards` 가 불필요하고,
`forwards` 를 쓰면 애니메이션이 끝난 뒤에도 `transform` 을 점유해
**호버(13px 분리)가 먹지 않기 때문.** 여기까지는 맞았다.

그런데 시점별로 캡처해 보니 **t=300ms 에 꽃이 이미 활짝 펴 있었다.**
꽃잎 애니메이션의 delay 가 최대 1.3s 인데, `backwards` 가 없으면 그 구간 동안
기본값(= 완성된 꽃)이 그대로 보이다가 시작 순간 `scale(.12)` 로 툭 튄다.

→ **`backwards` 만** 쓴다. delay 구간은 시작값으로 눌러두고, 끝난 뒤에는
   기본 CSS 로 돌려보내 호버가 정상 동작한다.

**검증** 240ms 줄기만 자라는 중 → 760ms 줄기 완성 + 봉오리 → 1120ms 꽃잎 펼침 →
완료 후 호버 시 초록 잎 분리 + `#7EE01D` 노출.

**교훈**
- **`forwards` 와 `backwards` 는 따로 판단한다.** `both` 로 뭉뚱그리면
  "delay 구간이 깨진다"와 "끝난 뒤 다른 규칙을 막는다"가 한 값에 묶여 버린다.
  이 케이스는 정확히 한쪽만 필요했다.
- delay 가 긴 스태거 애니메이션은 **시작 전 상태를 반드시 확인**한다.
  최종 프레임만 보면 멀쩡해 보인다. 시점별로 멈춰 봐야 드러난다.
- 끝난 CSS 애니메이션은 `getAnimations()` 에 안 잡힌다. 시점을 되감으려면
  클래스를 제거 → 리플로 → 재부여로 되살린 뒤 `currentTime` 을 준다.

### T26. HEX 라벨 간격 통일 — 원인이 세 겹이었다

**증상** 꽃잎마다 HEX 라벨의 간격이 제각각. 실측 중심→라벨 거리 **66 ~ 90px**.

**원인 1 — 텍스트 박스는 가로로 길다**
라벨을 `rotate(-r)` 로 역회전해 수평을 유지했는데, 박스가 약 30x7 이라
반지름 방향 두께가 방향마다 다르다. 위를 향한 잎은 h/2, 옆을 향한 잎은 w/2.
같은 거리에 두면 빈틈이 4배 차이 난다.

→ 축정렬 박스의 지지함수로 보정한다.

    e = (w/2)|dx| + (h/2)|dy|
    라벨 중심 = 꽃잎 끝 + dir * (GAP + e)

**원인 2 — 라벨이 꽃의 3D 변환 안에 있었다**
`.fx-flower` 의 `perspective + rotateY/X` 가 라벨까지 투영해
**위치마다 크기가 달라졌다**(실측 21x9 ~ 28x10). 보정식을 아무리 정확히 써도
입력값 자체가 흔들린다.

→ 라벨을 3D 밖 평면 레이어(`.fx-hexlayer`)로 빼고 JS 로 위치를 잡는다.
   박스가 전 잎에서 30x7 로 고정됐다.

**원인 3 — 좌표계를 섞었다 (여기서 한 번 더 틀렸다)**
1·2 를 고치고 재보니 여전히 **48 ~ 62px** 로 흔들렸다.
`getBoundingClientRect()` 는 카드의 3D 변환이 적용된 **화면 좌표**를 주는데,
`left/top` 은 레이어의 **로컬 CSS px** 다. 캐러셀 스케일(약 0.7) 때문에
두 단위가 다르고, 방향마다 보정량이 달라 어긋남이 균일하지도 않았다.

→ 화면 좌표를 로컬로 환산한 뒤 계산한다.

    const sc = box.width / layer.offsetWidth;
    const toLocal = (sx, sy) => [(sx - box.left) / sc, (sy - box.top) / sc];

**결과** 여섯 잎 전부 빈틈 **24px** (= GAP 11 + LIFT 13).
LIFT 는 호버 시 꽃잎이 바깥으로 나가는 거리와 맞춘 값 —
`pointerenter` 시점에는 아직 안 움직였으므로 미리 더해 둔다.

**가독성** `#3a2600` 9px → **`#241500` 10px + 밝은 헤일로**.
금색 배경 `#eda600` 대비 약 8.6:1. 헤일로(`text-shadow` 3겹)는 흰 꽃잎 위로
겹칠 때도 글자가 묻히지 않게 한다. tooltip 박스는 쓰지 않았다(사양 유지).

**교훈**
- **"간격이 안 맞는다"는 증상 하나에 원인이 세 개 있었다.** 하나 고치고 바로
  끝났다고 보지 않고 매번 다시 쟀기 때문에 2·3 이 드러났다. 수치 검증이 없었으면
  1 만 고치고 끝냈을 것이다.
- `getBoundingClientRect()` 와 `style.left` 는 **다른 좌표계**다. 3D 변환된 조상이
  하나라도 있으면 반드시 환산해야 한다. 이 프로젝트에서 rect 관련으로 어긋난 게
  T19·T22·T23 에 이어 네 번째다.
- 회전하는 요소에 라벨을 붙일 때는 **라벨을 회전 밖으로 빼는 편**이 거의 항상 낫다.
  안에 두면 크기·왜곡·기준점이 전부 방향에 따라 변한다.

### T27. GRAPHIC 카드 손 — 클리핑 경계, 3D 정렬, 그리고 알파에서 찾은 기준선

**요청** GRAPHIC 카드 선택 시 손이 뒤에서 나와 카드를 잡는 애니메이션. 레퍼런스 이미지대로.

**막힌 지점** 레퍼런스는 손의 약 20%가 **카드 위쪽 바깥**에 있다.
그런데 `.cfCard` 는 `overflow: hidden` 이라 카드 안에 넣으면 상단에서 잘린다.
`overflow` 를 풀면 fx 배경이 라운드 코너를 넘쳐 나오므로 불가.

**해결 — 트랙 레벨에 얹는다**
손을 카드가 아니라 `.cfTrack` 의 자식으로 붙였다.

    · 트랙은 overflow 제한이 없다 → 카드 위로 나올 수 있다
    · fitTrack 스케일을 카드와 함께 받는다 → 해상도가 바뀌어도 비율 유지
    · transform-style: preserve-3d → translateZ 로 카드 앞뒤를 정한다

카드 CSS·배치 계산식·라벨·클릭 로직은 하나도 건드리지 않았다.
통합 문서의 "carousel 코드를 추가하지 않는다" 를 어기는 유일한 지점이라
요소 하나 추가로 범위를 묶었다.

**1차 시도와 그 문제** 처음엔 카드 뒤(`translateZ(-220px)`)에서 앞(`+30px`)으로
나오는 모션으로 만들었다. 두 가지가 깨졌다.

1. **z 정렬 튐.** 손이 카드 평면을 통과하는 순간 `preserve-3d` 정렬이 뒤집히며 툭 튄다.
2. **filter 가 3D 를 평면화한다.** 그림자용 `filter: drop-shadow` 를 변환되는
   엘리먼트에 걸었더니 `preserve-3d` 컨텍스트가 깨져 카드와의 정렬이 어긋났다.

**2차 — 아래에서 올라오기, 그리고 그 문제** Z 를 고정하고 아래에서 튕겨 올라오게
바꿨다. 튐은 사라졌지만 손 이미지엔 손바닥이 없어서, 손이 최종 위치보다 아래로
내려가 있는 동안 **평평한 재단선이 카드 면 위에 떠서 잘린 손이 드러났다.**

**최종 — 손은 거의 제자리, 마스크로 드러낸다**
재단선은 카드 상단 모서리에 겹칠 때만 가려진다. 그렇다면 손을 크게 움직이지 말고
그 상태를 유지한 채 **위 → 아래로 드러내면** 된다.
- 래퍼(`.cfHand`): 8px 만 내려앉는다(`-174px → -166px`), Z 고정
- 안쪽 `img`: `mask-size` 를 `0% → 155%` 로 키워 상단부터 드러난다
  (불투명 구간이 마스크 높이의 66% 라 155% 면 정확히 전체를 덮는다. 처음에 220% 로
  뒀다가 절반 시점에 이미 다 드러나 연출이 사라졌다)
- 1250ms, `cubic-bezier(.4,.05,.3,1)` — 손끝이 모서리 위로 먼저 비치고 손가락이 내려앉는다
- `filter`·`mask` 는 둘 다 3D 를 평면화하므로 전부 안쪽 img 에, 변환은 래퍼에

**회귀 하나** 마스크 방식으로 다시 쓰면서 `.cfHand` 기본값의 `opacity: 0` 을 빠뜨려
**GRAPHIC 이 아닌 카드에도 손이 떠 있었다.** GRAPHIC 으로만 테스트해서 하루 늦게 발견.
기본 숨김 + `.is-on` 에서만 `opacity: 1` 로 되돌렸다.

**기준선을 알파에서 찾았다**
"카드 상단과 정확히 맞물리지 않는다"는 지적에 hand.png 의 알파를 행 단위로 훑었다.

    y=369 (높이의 42.3%) 에서 불투명 폭 804 → 648 로 급락

엄지 아래와 손가락 왼쪽이 같은 높이로 평평하게 잘린 선 —
원본 합성에서 **카드 상단 모서리였던 자리**다. 눈으로 맞출 값이 아니라 이미지가
이미 갖고 있던 값이었다. 이 선을 카드 상단(-200px)에 맞추면

    translateY = -200 + 0.077 * H,   H = W / 1.5
    W = 574  →  translateY = -166px   (실측 보정 -3.6px 포함)

W 는 손가락 좌우 범위가 레퍼런스와 같아지는 값으로 역산했다.

**검증** 재단선 − 카드 상단 = **0.8px**. 손가락 좌우 범위 **28.1~86.7%**
(레퍼런스 28.5~86%).

**표시 조건** `render()` 끝에서 `FEATURES[active].key === "graphic"` 일 때만 클래스를 붙인다.
클래스가 빠졌다 다시 붙으면서 애니메이션도 매번 재생된다.

**재현 못 한 것** 레퍼런스는 빨간 포스터의 위쪽이 약지·새끼손가락 **앞으로** 겹쳐
포스터를 손가락 사이에 낀 것처럼 보인다. 손은 카드 밖, 포스터는 클리핑된 카드 안이라
둘을 z 로 교차시킬 수 없다. 현재는 손이 카드 내용 전체 앞에 있다.
교차가 꼭 필요하면 손 이미지를 손가락 단위로 분리해 카드 안팎에 나눠 배치해야 한다.

**교훈**
- **클리핑 경계가 곧 배치 결정이다.** "카드 안 어디에 둘까"가 아니라
  "카드 안이냐 밖이냐"가 먼저였다. overflow 를 먼저 확인했다면 시행착오가 없었다.
- **`filter` 는 `preserve-3d` 를 평면화한다.** 3D 컨텍스트 안에서 그림자가 필요하면
  변환하는 엘리먼트와 필터를 거는 엘리먼트를 분리한다.
- **3D 평면을 통과하는 애니메이션은 정렬이 뒤집히는 순간 튄다.** 앞뒤 이동이
  연출에 꼭 필요하지 않으면 Z 를 고정하는 편이 안정적이다.
- **잘린 컷아웃은 움직이지 말고 드러낸다.** 이미지의 잘린 경계가 가려지는 위치가
  하나뿐이면, 그 위치에 고정한 채 마스크로 등장을 연출하는 편이 깨지지 않는다.
- **"보여야 할 때"만 테스트하면 "안 보여야 할 때"를 놓친다.** 조건부 요소는
  조건이 거짓인 상태도 반드시 확인한다.
- **컷아웃 이미지의 알파에는 원본 합성의 기준선이 남아 있다.** 눈대중으로 맞추기 전에
  알파를 훑어보면 정답이 이미 들어 있는 경우가 있다.
- 또 stale rect 에 당했다(T19·T22·T23·T26 에 이어). `navigate` 와 같은 배치에서 잰
  값은 -21%/276px 같은 헛값이었고, 별도 호출로 재니 0.8px/28.1% 로 정확했다.

### T28. GRAPHIC 손 — 두 장으로 잘라 카드 앞뒤에 나누고, 무게로 카드가 내려앉는다

**요청** 손 에셋을 새로 만들어 정말 슬금슬금 기어올라와 카드를 잡고,
손 무게에 GRAPHIC 카드가 20% 아래로 45° 각도로 쿵 내려앉게. 기어오름은 더 천천히.

**에셋 — 새로 그린 게 아니라 잘라서 다시 만들었다**
원본 hand.png 에는 손바닥이 없다. 이미지 생성 도구가 없어 사진처럼 손바닥을
새로 그려 넣을 수는 없었다. 대신 알파에서 찾은 재단선(y=369, 높이 42.3%)에서
두 장으로 나눴다.

| 파일 | 내용 | 위치 |
|---|---|---|
| `hand-knuckles.png` | 손등 마디 + 엄지 (원본 0~368행) | 카드 **뒤** z −2px |
| `hand-fingers.png` | 손가락 몸통 + 손톱 (원본 367~871행, 2행 겹침) | 카드 **앞** z +2px |

뒤 레이어가 카드 상단 아래에 있는 동안 그 잘린 선은 **카드에 실제로 가려진다**
(preserve-3d 깊이 정렬). T27 까지 계속 문제였던 "움직이면 잘린 면이 드러남"이
구조적으로 사라졌다. 2행 겹침은 경계 헤어라인을 막는다.

**리그(.cfGrab)** 활성 카드와 같은 박스(500x400, 트랙 중심)를 트랙에 둔다.
활성 카드의 캐러셀 변환은 `translate(-50%,-50%)` 뿐이라 좌표가 같고,
카드와 리그에 같은 낙하 변환을 걸면 손이 그대로 붙어 따라간다.

**타임라인** 총 약 4.4초

| 구간 | 시작 | 길이 | 내용 |
|---|---|---|---|
| 대기 | 0 | 800 | 카드가 가운데로 들어오는 동안. 그 전엔 카드가 뒤 레이어를 못 가려준다 |
| 기어오름 | 800 | 2600 | 손끝 19px 빼꼼 → 멈칫 → 반쯤 → 멈칫 → 끝까지. 미세 회전 ±1.4° |
| 넘어옴 | 3240 | 440 | 손가락이 카드 상단을 경첩으로 rotateX 100° → −7° → 0° |
| 쿵 | 3640 | 720 | 카드+리그 translateY 80px(20%) + rotateX 45°, 한 번 튕기고 안착 |

**카드를 어떻게 움직였나** 카드는 캐러셀이 인라인 `transform` 을 쓴다.
덮어쓰면 캐러셀이 깨지므로 WAAPI `composite: 'add'` 로 그 위에 **더했다**.
배치 계산식(render)은 손대지 않았다. `add` 를 못 쓰는 브라우저에선 낙하만 건너뛴다.
다른 카드로 넘어가면 손은 즉시 숨기고, 내려앉은 카드는 2.5배속 역재생으로 되돌린다.

**45° 해석** "45도 각도로 내려간다"를 **상단이 뒤로 젖혀지는 rotateX(45°)** 로 읽었다.
손이 뒤에서 모서리를 쥐고 끌어내리면 위가 뒤로 넘어가는 게 물리적으로 맞다.
`GRAB.TILT`, `GRAB.DROP_Y` 한 줄로 바꿀 수 있다.

**정리** 예전 카드 내부용 손(`.fx-graphic-hand`)은 존재하지 않는 `/graphic-hand.png`
를 참조하던 죽은 코드였다(Vite 가 없는 경로에 index.html 을 200 으로 돌려줘서
에러 핸들러가 조용히 지우고 있었다). 걷어냈다. `public/hand.png` 사본도 삭제.

**검증**
- 1700ms 손끝 빼꼼 / 3000ms 반쯤 / 3560ms 손가락 넘어옴 / 3700ms 쥠 /
  3990ms 쿵(튕김) / 5000ms 안착 — 시점별 정지 캡처로 확인
- 안착 후 손가락 레이어 높이 155 → 107px (cos45° × 155 ≈ 110) — 카드와 같이 젖혀짐
- UI 로 이동 시 GRAPHIC 카드에 남은 add 애니메이션 0, 리그 숨김, 배치 정상
- "손가락이 반투명해 보인다" → 카드를 숨겨 보니 완전 불투명. 원본 사진의 밝은
  윗마디 피부톤이 밝은 카드 위에서 그렇게 읽힌 것

**한 번 헷갈린 것** 실재생 6초 뒤 화면이 카드들이 겹친 이상한 상태였다.
`active` 는 이미 graphic 인데 모든 카드의 CSS 전환이 `running` 인 채 직전 위치에
멈춰 있었다. 브라우저 페인이 사용자 화면에 안 보이는 동안 프레임을 안 그려서
생긴 일로 보이며, 잠시 뒤 다시 보니 정상 안착해 있었다.

**교훈**
- **잘린 컷아웃은 "가려지는 쪽"에 두면 잘린 면이 공짜로 숨는다.** 마스크로 흉내 내지
  말고 실제 깊이 정렬에 맡겼더니 T27 의 문제가 구조적으로 사라졌다.
- **남이 쓰는 transform 을 움직여야 할 때는 덮어쓰지 말고 더한다.** WAAPI
  `composite: 'add'` 는 캐러셀 계산식을 건드리지 않고 그 위에 연출을 얹는다.
- 같은 연출에 쓰던 옛 구현이 남아 있지 않은지 먼저 찾는다. 조용히 실패하는
  죽은 코드는 다음 사람을 헷갈리게 한다.

### T29. GRAPHIC 손 — 모션 원칙으로 다듬기 (계단 → 유기적, 관통 → 튕김, 즉시 → 예비동작)

**요청** motion-design 원칙 기준으로 T28 손 연출 다듬기.

**점검 방법** 재생 중인 WAAPI 애니메이션을 전부 `pause()` 하고 `currentTime` 을 지정해
시점별 정지 프레임을 뽑아 한 장으로 모아 봤다(T10 교훈 — 실시간 캡처는 믿지 않는다).

**발견 → 수정**

| 구간 | 문제 | 수정 |
|---|---|---|
| 기어오름 | 대칭 ease-in-out + 완전 정지 2회 → 계단처럼 기계적 | 빼꼼 → **움찔 물러남**(4~5px) → 머뭇(1~2px 흘러감) 2회 + 끝에 −3px 넘침. 구간별로 감속/빠른 움찔/느린 머뭇 이징을 따로. x ±3px 로 경로가 호를 그린다 |
| 넘어옴 | 오버슈트 −7° → 손끝이 카드 평면을 ~19px 파고듦 | 0° 에 철썩 닿고 **바깥(+4°)으로 튕겼다** 붙는다. 오버슈트는 항상 + 쪽 |
| 쿵 | 손가락이 닿자마자 낙하 → 무게가 안 읽힘 | `BEAT` 90ms 쥠 + 낙하 앞 16% 를 예비동작으로(카드 5px·1.5° 눌림). `DROP` 720 → 880 |
| 2차 동작 | 손이 카드와 완전히 같은 몸 → 납작함 | 예비동작 때 마디 3px 쥐어짐, 충돌 순간 손가락이 관성으로 +6° 들렸다 붙음 |

2차 동작 애니메이션은 `fill: "forwards"` — `both` 면 대기 중에 앞 구간(넘어옴)의 값을 덮는다.

**검증** 1350~4700ms 16프레임 정지 캡처: 관통 없음, 예비동작·들림 확인.
GRAPHIC 안착 후 다른 카드로 이동 → 리그 opacity 0, 남은 `composite:add` 0, 페이지 에러 0.

**교훈**
- **3D 면에 닿는 오버슈트는 방향을 본다.** 면을 지나치는 쪽은 깊이 정렬에 잘린다. 바닥에 닿는 물체는 통과하지 않고 튕긴다.
- **"멈칫"은 정지가 아니다.** 완전히 서면 기계, 살짝 물러났다 흘러가면 생물.

## 4. 설계 결정 기록

의도적으로 선택했고, 나중에 이유를 잊기 쉬운 것들.

| 결정 | 이유 |
|---|---|
| 라우터·상태관리 라이브러리 미사용 | 단일 페이지 + 소수 컴포넌트 규모에서 불필요. 의존성이 늘수록 커스텀 인터랙션을 방해 |
| 캐러셀 위치를 React state로 관리하지 않음 | 매 프레임 리렌더 방지. `MotionValue` + rAF로 직접 DOM 갱신 |
| 폰트 크기를 실제 개수가 아닌 고정 `VISIBLE=10` 기준으로 계산 | 레퍼런스가 늘어나도 화면 밀도가 변하지 않도록 |
| 휠 이벤트의 `deltaY` 크기를 무시하고 방향만 사용 | 트랙패드/일반 휠의 delta 값이 장치마다 제각각이라 신뢰 불가. "1이벤트 = 1행"으로 고정 |
| 3D 로고 앞면에 `zIndex: 1` 명시 | `preserve-3d` 깊이 정렬 미지원 환경에서 뒷면이 앞면을 덮는 것 방지 |
| 모바일에서 데스크탑 물리 연출 제외 | 좁은 화면에 여러 인터랙션이 밀집하면 오히려 어색해짐 |
| 커버 이미지를 외부 스크린샷 서비스 대신 SVG 생성으로 | 저작권 관점에서 안전 (현재는 텍스트 온리로 전환, 코드는 제거됨) |
